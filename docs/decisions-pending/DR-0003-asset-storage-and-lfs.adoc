= DR-0003: Where do binary game assets live, and does this repository use Git LFS?
:status: OPEN
:opened: 2026-09-27
:guard: none yet — see "Guard"
:files: .gitattributes, .gitignore

== Question

Three linked questions that have to be answered together, because the answer to
the first determines the others:

. When real binary assets land — textures, audio, meshes, cutscene video — do
  they go in this repository at all, or in a separate content repository or
  object store?
. If they go here, are they tracked as ordinary Git blobs or through Git LFS?
. Either way, does the generated `assets/` tree get committed, or is it built at
  package time from the authored `source/` tree?

== Why it is not decidable here

The repository currently tracks **zero** binary assets. There is nothing to
measure: no total asset size, no largest single file, no churn rate, no history
of how often an asset gets revised. Every one of those numbers is what the
answer depends on, and none of them exists yet.

`git-lfs` is also not installed in the development sandbox and no
`filter.lfs.*` entries are configured, so the LFS path could not be exercised
even provisionally.

This question is therefore **not yet live**. It becomes live the first time a
real texture, sound or cutscene is committed, and it should be ruled before that
happens rather than after, because the after-case is a history rewrite.

== What was found instead

* The estate's canonical `.gitattributes` (`rsr-template-repo`, standards#343
  phase 1) contains **no** `filter=lfs` attribute anywhere. Nothing in
  `hyperpolymath/standards` mentions Git LFS. So LFS is not an estate convention
  and adopting it here would be a per-repo departure needing its own reasoning.
* IDApTIK's `.gitattributes` was diverging from canon in ways unrelated to
  assets: it declared `diff=zig`, which canon explicitly records as *not a
  driver git ships* (measured on git 2.47.3 — git silently falls back to the
  default heuristic), and it was missing most of canon's language, binary and
  lockfile rules. It was replaced with canon verbatim plus a clearly separated
  per-repo addendum on 2026-09-27.
* The addendum now declares every asset extension the finished game will plausibly
  carry — audio, video, textures including `ktx2`/`basis`, meshes, fonts, WGSL
  and SPIR-V — as `binary` or `text` as appropriate. Declaring them before any
  asset exists is deliberate: a type first declared *after* a file of that type
  is committed means that file was already normalised to LF on the way in, and
  fixing it is a re-commit of every asset touched.
* `.gitattributes` marks `assets/**` as `linguist-generated=true` with diffs
  suppressed, on the assumption that `assets/` is derived from `source/`. That
  assumption is question 3 above and is **not settled**.
* The licence layers constrain this. Game content is CC-BY-SA-4.0 and the engine
  is AGPL-3.0-or-later (AGENTS.md, inviolate). A separate content repository
  makes that boundary mechanical rather than conventional, which is an argument
  for option B below that has nothing to do with storage efficiency.

== Current state

No binary assets. No LFS. `.gitignore` already excludes importer scratch, DCC
autosaves, audio-editor peaks, video proxies, shader caches and Bevy runtime
scratch, so that machinery cannot be committed by accident when it arrives.

== Options

[cols="1,3,2", options="header"]
|===
|Option |What it means |Cost

|A. Ordinary Git blobs in this repository
|Simplest. Works everywhere with no client dependency. A plain `git clone`
produces a runnable game.
|Every asset revision is stored forever. A repository with a few hundred MB of
audio and textures that get re-exported regularly becomes multi-GB to clone, and
there is no way to shrink it afterwards short of rewriting history.

|B. Separate content repository or object store
|Keeps the engine repository small and makes the AGPL / CC-BY-SA-4.0 licence
boundary a repository boundary rather than a directory convention.
|Two repositories to keep in step. A build needs both. Version skew between
engine and content becomes a real failure mode needing its own pinning
mechanism — which this repository already knows how to do for the Idris2 ABI,
but it is work.

|C. Git LFS in this repository
|Keeps history small and one repository. Standard practice for games.
|`git-lfs` becomes a hard build dependency. A clone without the client silently
produces pointer files instead of content — the failure is quiet and confusing.
The estate does not use it, so IDApTIK would be the first, and LFS storage and
bandwidth are billed separately by the host.
|===

A fourth option — commit `source/` only and generate `assets/` at package time —
is orthogonal and can be combined with any of the three. It is the most
attractive for review quality, because it means a regeneration commit is a diff
of authored text rather than forty thousand lines of derived output, and it is
what the current `linguist-generated` marking already assumes.

== What a ruling unblocks

* The whole content pipeline: `source/art/`, `source/audio/`, `source/video/`
  and their `PIPELINE.md` documents cannot say where their output goes until
  this is answered.
* Whether `assets/` is committed at all, and therefore whether the
  `linguist-generated` marking in `.gitattributes` is correct or should be
  removed.
* Repository size budgeting. If the answer is A, a size ceiling should be set
  now, while the repository is small enough that staying under it is free.

== Guard

None, and that is itself the point. There is nothing to check because nothing
exists. Two guards become appropriate the moment this is ruled:

* If A or C: a check that no committed file exceeds a stated size ceiling, so
  the ceiling is enforced by a gate rather than by memory.
* If C: a check that `git lfs env` succeeds in CI and that every path matching an
  LFS-tracked pattern is actually stored as an LFS object, because the failure
  mode of a half-configured LFS repository is a pointer file committed as a blob.

Until then the honest state is that this is undecided and unguarded, recorded
here rather than silently resolved by whoever commits the first texture.
